# 后续完善规划

v0.4 先把「固定目标 → 受控执行 → 核验交付」做成可复现的小闭环，避免以工具成功代替任务完成。以下是建议实施顺序，不是已完成能力。

| 顺序 | 工作 | 进入下一阶段的证据 |
| --- | --- | --- |
| 1 | Ollama/OpenAI 真实模型集成；核对 Pi 当前 CLI、结构化输出与缺失 usage；标准化错误分类 | 固定小任务、超时、错误 JSON、澄清与重启的真实 provider 记录；UNKNOWN 无重复调用 |
| 2 | 将 P1/P2 账本迁入事务级端口；补故障注入矩阵、旧版本升级和孤儿对象 GC | 每个 effect cut-point 有对账测试；迁移后账本/预算与交付一致 |
| 3 | 增加受管目录树、diff 编辑；独立测试/编译验收适配器；分离候选与验证执行环境 | 验收在固定候选上运行；错误代码带成功写入收据仍拒绝交付；原文件不受影响 |
| 4 | ContextCompiler 与检索端口：先文件/关键词检索，再向量召回；长期记忆带来源、版本和失效规则 | 可测检索质量；更正不丢失；过期记忆不能升级为当前授权或执行事实 |
| 5 | 改善导入/导出、任务模板、流式进度和无障碍；按需要扩展部署边界 | 真实任务可独立操作；重连不重复提交；发布环境明确身份、权限和数据隔离 |

每一步坚持纯领域规则、端口合同、独立适配器和可审查事务边界。分布式执行、任意 shell、多 Agent 与自我进化没有当前验收前提，暂不扩张。
