# Myth v0.10 整体诊断与本轮优化

日期：2026-10-03。基线：`c1026a6402e78138bf3df1fec718a583a192675a`（GitHub HEAD 实际核对）。修改分支：`codex/context-continuity`。

## 1. 总体判断

**现有单机 Runtime 值得继续沿用，当前最有价值的进展是提高真实任务的连续完成能力。** Run/Ticket/Receipt、模型请求复用、不可变文件交付、精确验收和进程中断恢复已有实现与回归证据。Core / Domains / Strategies / Adapters 的方向也能容纳后续变化，没有必要再次调整全仓目录或重做内核。

但架构地图的广度已经领先于运行链的深度。Intent Pick、Information Resolution/Gain、Workflow、Multi-Agent 等大部分还没有接管请求；Context、Memory、Control 等已接入模块之间反而存在可复现的衔接问题。继续增加合同能表达方向，却未必提高下一次任务的成功率。

本轮选择打通一条具体链：**资料与历史增多 → 上下文取舍 → 连续工具调用 → 用户 Compact/Pause → 可观察的完成结果**。没有增加依赖、引入另一套 Agent Loop 或变更数据库表结构。

用户提供的《AGENT 开发架构与实施指南》仅用于参考状态归属、上下文投影和证据边界；本轮以 v0.10 的实际装配与行为为准。

## 2. 各模块诊断

| 模块 | 代码中的实际状态 | 判断与建议 |
| --- | --- | --- |
| Durable Runtime / Store | 有事务预算、执行 Ticket、收据、UNKNOWN 与恢复；原有子进程硬退出测试通过 | 是项目最扎实的基础。继续复用，不做全量重写 |
| Conversation / Agent | 对话与精确验收拥有各自用例，共用底层模型与执行事实；普通回答完成与目标验收分开 | 产品路径合理。优先评测真实多步任务，不能用 schema 或 mock 通过率代替任务能力 |
| Control | Pause/Resume/Stop/Steer/模型切换已持久化；有调用后安全点 | 顺序命令可用；并发提交和跨状态转换还缺一致的事务边界。本轮修复 Compact 消费时机及 PAUSED 占用会话问题 |
| Context | 原版只有历史消息参与预算，知识、记忆、工具结果全部视为必需 | 直接阻断长任务，故作为本轮主改进；现在可分项取舍并记录投影证据 |
| Knowledge | UTF-8 分块、关键词排序、项目范围和来源引用真实可用 | 候选先截断后排序；显式附件可能只附带匹配片段或前 1,000 字符，模型没有独立全文分页读取工具。应先补证据展开，再加向量检索 |
| Memory | 类型、当前 revision、撤销、关键词召回、自动 episode 写入已接通 | 当前是全工作区召回，revision 更新覆盖当前行，未保存完整旧版本链。需要明确个人共享偏好与项目经历的区别 |
| 项目工具 | read/search/diff/git 只读能力、生成受管副本均存在 | 下一步补充“读取原文 → 生成候选 → 固定候选验证”的真实闭环。项目搜索遍历方式还有明显规模成本 |
| Goal / Trigger / Personal State | 有持久化 API、Goal↔Run 关联；Trigger 不启动后台任务 | 适合保留现有合同。Goal 关联失败目前可能留下半完成提交，见下文复现 |
| Intent / Information / Coordination | 有纯类型、协议、注册表；`send()` 仍直接进入对话 Agent | 保持 exists 等成熟度陈述。Direct 当前主要是 Loop 首步回答，不是已实现的零模型 Intent 快路 |
| Evaluation / Evolution | 有质量门函数和候选策略合同 | 尚缺固定真实任务集与可比较运行记录；这是后续路由、Gain 和自动演进的共同前置条件 |
| Web / Inspector | 原生页面和本地 HTTP 可用，执行/预算/控制事实可见 | 本轮增加模型实际上下文字节与取舍数量；全会话轮询会随着历史、结果、事件增长而变重 |
| Provider / 发布验证 | Ollama 非流式适配；OpenAI/Pi 有适配代码与替身测试；CI 为 Ubuntu/Python 3.12 | 当前 Windows/Python 3.13.9 回归通过。真实模型质量、远端适配、旧活跃任务完整升级仍需单独验证 |

## 3. 本轮已经修复

### 3.1 上下文预算从“历史截断”变为完整投影

新增纯函数模块 `src/myth/conversation_context.py`，继续使用已有 `ContextCompiler`：

- 必需：系统/项目指令、Steering、本轮初始任务及全部澄清、显式附件已固定的片段、最新工具结果、已生成文件的产物事实。
- 可选：较旧工具预览、自动检索片段、上一轮以前的聊天历史、自动召回 Memory；按确定的优先级和顺序选入。
- 较旧的 `content/output/diff` 折叠为标记清楚的预览；检索结果保留来源，产物保留摘要和 evidence_ref。完整执行记录不被改写。
- 42,000 字节按实际消息列表 JSON 的 UTF-8 大小计算，包含 role、转义与消息分隔开销；远端传输说明也在编译前加入。
- `turn_message_start` 固定本轮边界，Compact 只限制此前的历史，不能再把本轮原始要求裁掉。
- `attached_document_ids` 区分明确附加资料与自动召回。旧快照没有这个字段时保守保留其知识片段；旧轮次边界从已有持久消息推导，无需修改旧数据库。

该策略是可复现的字节预算基线，不是语义摘要、tokenizer 或已经校准的 Information Gain。

### 3.2 每次投影有持久证据

`ModelRequest.context_report` 保存实际选入/未选入/折叠的来源标识、字节、策略版本及 control revision。报告随请求存进不可变对象；`ConversationContextCompiled` 事件与模型 Ticket 在同一个事务提交。

因此：编译失败不会冒出“已调用模型”的上下文事件；复用同一模型收据不会新增一次编译事件。provider 适配器仍只发送其支持的消息与 schema 字段，不会把这份本地审计元数据额外塞进远端协议。

Inspector 显示最新已发出模型请求的字节、选入项数、旧记录折叠数和未选入项数。它表示该次模型实际使用的投影，不等于整个会话或整个知识库的大小。

### 3.3 Compact 和 Pause 的连续性

原版在每次模型返回后无条件消费当前 Compact 标记。用户在调用途中点击 Compact 时，这个请求根本没使用压缩上下文，命令却已消失。

现在按该决策真正绑定的不可变请求检查 `context_report`，仅当请求使用了 Compact、且 control revision 仍匹配时才确认消费。模型收据恢复复用也不能误消费一个新命令；期间又有控制变化时，宁可把 Compact 留到下一次调用。

PAUSED 纳入会话的活跃状态集合：暂停后不能创建第二个并行轮次，也不能直接归档会话。页面在暂停状态下仍显示 Stop，使用户可以直接结束这一轮。

## 4. 修复前后证据

| 场景 | 基线行为 | 修改后 |
| --- | --- | --- |
| 六条召回 Memory，共 47,520 UTF-8 字节 | 在模型调用前 ContextBudgetError | 选入四条、未选入两条；包含指令和当前任务的消息为 34,717 字节 |
| 连续两次约 23,400 字符的工具输出，再回答 | 两份输出累计进入必需上下文，轮次 FAILED | 第三次模型调用完成回答；旧结果折叠，两个完整收据保持原样 |
| 本轮原始要求后有十条澄清消息，再 Compact | 原始要求被最后八条历史截断丢失 | 原始要求和十条澄清全部保留 |
| 自动检索很多资料，同时固定一个附件 | 召回内容挤爆必需预算 | 附件片段保留，可选召回让出空间 |
| Compact 在模型调用过程中到达 | 模型返回时误消费 | 下一次模型请求实际使用 Compact 后才确认 |
| 模型收据已落盘、步骤未绑定时中断，随后 Compact | 收据复用仍可能误消费新命令 | 从真实旧请求报告判断，新命令留到下一次调用 |
| 暂停后发送另一条新请求 | 同一会话允许两个未结束轮次 | 第二条被拒绝，Resume 完成后可正常创建下一轮 |

这些数据来自确定性 fixtures。它们验证的是 Runtime 行为与上下文预算，不是模型理解准确率。

## 5. 整体诊断中仍存在的具体问题

以下不是推测，也没有包含在“本轮修复完成”之内。复现脚本为 `scripts/diagnose_v010.py`，只使用临时数据库和本地替身，不连接模型，不读取用户项目。

### 优先处理：Control 并发命令

位置：`platform/control_store.py::command`。读取 turn/current snapshot、计算新 revision 在写事务之外。两个连接在这个窗口交错，都会选择相同 revision；复现中第一条 Steer 抛出 `IntegrityError: UNIQUE constraint failed: workspace_control_commands.run_id, workspace_control_commands.revision`，steering 没有保存。

建议下一轮把**读取当前状态 → 合法性判断 → revision 分配 → 命令与状态投影写入**收进同一事务；同时覆盖 Pause/Resume/Stop 与模型返回的交错。无需引入消息中间件或新 Control 层。

### 优先处理：Goal 关联的半完成提交

位置：`web_workspace.py::send`。先提交 Turn，再调用 `personal.bind_run`，之后才启动 worker。传入不存在的 `goal_id`，API 抛出 KeyError，却已经创建一个 RUNNING 轮次且没有启动 worker。

建议先校验 Goal，并让可选关联与 Turn admission 共用事务边界；把 Goal 身份纳入入口去重语义。验收应覆盖无效 Goal、同 request_id 改 Goal、失败后重试。

### 产品语义需明确：Memory 的范围和事实等级

位置：`platform/memory_store.py::search/record_episode`、`web_workspace.py::send`。项目 A 的 episode 在项目 B 的同关键词请求中被实际召回；Knowledge 的项目过滤不适用于 Memory。这不等于多用户隔离漏洞，因为产品当前是单用户，但会把不相关项目的经历带进新任务。

建议显式区分 global preference 与 project/session episode；默认只召回当前范围和明确共享项。还需保留“这是模型说过的话”与“这是外部验证事实”的区别，避免回答经过 episode 再召回后被误当权威事实。当前 `remember` 的 revision 是当前值版本号，不能宣传为完整历史版本库。

### 中等规模就会出现：检索候选截断

位置：`adapters/workspace_store.py::search`。SQL `LIMIT 10000` 发生在 Python 排序之前，且无相关性筛选。构造 10,001 块，唯一精确匹配放在索引 10,000，查询返回 0 项。Memory 也只对最近 500 条记录进行匹配。

建议保留关键词评分基线，先补完整候选召回/可分页索引与覆盖测试，再比较向量和 rerank。这样才能区分“排序差”和“根本没进入候选集”。

### 静态发现：搜索与前端投影的规模成本

- `conversation_execution.py::_iter_text_files` 先 `sorted(path.rglob('*'))`，随后才排除目录与应用 2,500 文件上限。上限限制的是选中文件数，不能限制此前的遍历/排序工作。建议用可剪枝遍历，再明确 scanned/truncated/next_cursor。
- `workspace_store.py::session` 加载完整 messages、turns、activities；Web 继续加载每轮 operations/events；浏览器周期拉取。下一轮可为当前 Turn 增量取事件，为历史分页。先测 payload 和延迟，不必立即引入 WebSocket。
- 工具最新结果仍是必需信息；单次特别大的中文 diff、长项目指令、过多必需澄清仍可能超过 42 KB。本轮会如实在 Ticket 前停止。后续应给工具补按字节分页、摘要地址和读取能力，不能靠悄悄切断最新证据解决。

## 6. 推荐推进顺序

| 顺序 | 小步交付 | 完成标准 |
| --- | --- | --- |
| 1 | 修 Control 并发与 Goal admission；增加跨连接交错测试 | 每个被接受命令恰有对应 revision；无效 Goal 不留下半创建轮次 |
| 2 | 给 Memory 增加显式范围与来源事实等级；补 `knowledge.read` 原文分页 | 项目问题不自动带入其他项目 episode；引用可展开到固定 digest 下的原文 |
| 3 | 固定一组真实任务评测：问答、连续读取、资料导航、文件生成、澄清、暂停恢复 | 记录完成率、错误类别、实际模型用量/耗时、产物证据；保留失败样本与模型版本 |
| 4 | 用当前 Information Resolution 合同接入“片段 → 原文证据”一条链；再尝试确定性 Intent 快路 | 同一 source_ref/digest 可展开；简单算术等显式任务走较低成本路径，其余稳定回退 Agent |
| 5 | 增加一种固定 profile 的本地测试执行，再扩充 Workflow/AgentPort | 一个真实修改任务能生成候选、运行指定验证、交付结果；使用已有 Ticket/Receipt/预算 |

Information Gain 可以先观察“新增证据是否改变最终答案或减少后续读取”，积累可比较样本，再讨论 estimator。Information Delta 最自然的落点是 Memory 更新、撤销与冲突记录。两者都有现实数据来源后，才值得改变路由策略。

## 7. 验证与复用

当前环境：Windows / Python 3.13.9。最新基线原有 **96 项测试通过**；修改后 **110 项测试通过**，包括新增 14 项上下文/连续性测试及扩展的真实 HTTP 投影断言。Python 编译、两份 JavaScript 语法检查和 diff 空白检查通过。

浏览器实查：离线确定性样例的会话显示 COMPLETED，Inspector 显示 `34701 / 42000 bytes`、折叠 1 项、未选入 6 项；暂停样例中 Stop 可用且 Resume 可见。浏览器无捕获到的 JavaScript error。没有进行本轮全量手机布局或跨浏览器矩阵。

本机 `127.0.0.1:11434` 当时拒绝连接，因此本轮没有真实 Ollama 质量测试，也未进行 OpenAI/Pi 真实调用；文档中旧版的模型实测记录不算本轮证据。
